## Session 11 (2026-10-13): systematic multilingual testing, and the fixes it forced
User asked for extensive testing in every supported language, then a web version that works reliably before the mobile app. There is nothing to "train" in this system (pretrained ASR/embedding/LLM + RAG), so the work was: build an evaluation set, measure, find failures, fix, re-measure. Everything below was measured, with raw results in `experiments/results/` (`eval_v1_run1..N.jsonl`, `stress_run*.jsonl`, `probe_unanswerable.json`, `evidence_check_eval.json`).

**Evaluation assets (new).** `data/evaluation/questions_v1.json`: 20 questions x 6 languages (12 answerable, 4 off-topic, 4 live-information). **Caveat: written by the AI assistant, translations not reviewed by native speakers; "expected category" is a proxy label, not human relevance judgement.** Good for regression testing, not for publication claims. Scripts: `evaluate_pipeline.py` (runner), `summarize_eval.py` (per-language table + threshold sweep), `benchmark_retrieval.py`, `probe_unanswerable.py` (20 off-topic/near-topic probes), `eval_evidence_check.py`, `stress_api.py` (30 odd/hostile inputs + voice round-trip + bad audio), `health_check.py` (pre-flight).

**Headline result (text pipeline, 72 answerable + 24 off-topic + 24 live items):**

| | Baseline (run 1) | Final code (run 5) |
|---|---|---|
| Answerable questions answered | 87.5% (63/72) | 100% (72/72) |
| Off-topic questions refused | 100% (24/24) | 100% (24/24) |
| Live-info handled with disclaimer in the user's own language | 71% (17/24) | 100% (24/24) |
| Median latency | 6.3 s | 8.9 s (extra LLM evidence check) |

**Read these numbers carefully:** the fixes were designed while looking at failures on this same 20-question set, so run 5 is *training-set* performance, not an unbiased estimate. Independent signals are weaker but real: the 30 stress inputs and 20 off-topic probes (the probes did inform the evidence-check prompt). Runs 2 and 3 in `experiments/results/` are superseded intermediate configurations (run 2 was stopped early). Full test suite: 55 passing.

**Bugs found and fixed (each has a regression test):**
1. *Abstention gate read a placeholder score.* BM25-only chunks had `dense_score=0.0`; the gate looked at `results[0]`, so answerable questions (cyclone preparation: 5/6 languages) were refused. Now every chunk carries its exact cosine (`hybrid.py::_exact_cosine`), and the gate uses the best dense score of the top 5.
2. *Generation was non-deterministic* (no temperature/seed): same evidence, different advice per run. Now `temperature=0, seed=0`.
3. *BM25 matched on function words* ("what should I do if my"), pulling forest-fire/earthquake chunks into flood answers. New `lexical_tokens()` (stopwords + light plural stemming) for index and query; fusion MRR 0.822 -> 0.844, top-1 hazard hit 73.6% -> 80.6%. Fusion strategies compared: current min-max hybrid (MRR 0.844) vs RRF (0.844, lower top-1) vs dense-only (0.734) vs BM25-only (0.819) -> kept the hybrid.
4. *Embedding similarity cannot separate on- from off-topic* (off-topic scores up to 0.855, answerable ~0.85-0.91). Added an LLM yes/no evidence check (`safety/evidence_check.py`) with a strict prompt plus a lenient second chance only when the question names a hazard and the top passages are from that hazard's category. Measured on 12 answerable + 20 off-topic probes: 12/12 kept, 20/20 refused. **Limits: small sample, LLM judgement not a calibrated probability; ablate with `--no-evidence-check`.**
5. *The word "help" returned fire-alarm instructions.* New vague-query rule (`safety/query_check.py`): fewer than 2 content words and no (fuzzy-matched) hazard word -> ask what is happening and show 112/1070/1077, in all 6 languages.
6. *Live-info guard missed translation variants* ("still closed", "today", "ordered to evacuate") and only had English/Tamil disclaimers. Patterns widened; Hindi/Telugu/Kannada/Malayalam disclaimers added (machine translated, unreviewed).
7. *Translator mistranslated hazard words* (Hindi "लू" -> "Lu", Telugu "వడగాలులు" -> "dust storms", Kannada "ಬಿಸಿಗಾಳಿ" -> "hot wind"). Added a deterministic stem-based hazard glossary applied before the LLM (`translation.py::HAZARD_GLOSSARY`). Also removed a prompt line I had added that told the translator "this is a disaster question": with garbled speech-recognition input it invented disaster questions from noise (cricket question answered with disaster tips).
8. *Voice endpoint returned HTTP 500 on empty/corrupt audio.* Now returns a friendly retry message.
9. *Silence was transcribed as a Norwegian subtitle credit* (Whisper hallucination) and answered; now `vad_filter=True`, and recordings detected as an unsupported language are rejected with a clear message instead of being answered in English.
10. *Speech recognition:* Whisper `small`/`medium` transcribed spoken Telugu/Kannada/Malayalam as Devanagari transliteration (correct script on 4/10 test clips for medium). `large-v3` (int8_float16, ~2.5 GB VRAM) gets Telugu/Kannada right; Malayalam still wrote Gurmukhi, so `transcribe()` retries once with a short in-language prompt when the output script does not match the detected language (verified to produce Malayalam script, text still imperfect). CPU fallback on CUDA OOM. Latency ~3-6 s per short clip.

What changed, and what did not work:
1. **Speech output is fetched after the text** (`with_audio=false` + `/api/tts`; "Listen" button on every answer; auto-fetched after a spoken question). Tamil/Kannada synthesis (MMS VITS on CPU) alone was ~10 s of a ~25 s round trip; audio for those two still takes ~8-10 s but arrives while the user reads. ## Session 10: real on-device speech-to-text (the last network-dependent piece)
User asked directly what to install for a "total offline app" with speech-to-text AND text-to-speech both working with no network. Investigated rather than assumed:

- **Text-to-speech**: no code gap -- Android's built-in `TextToSpeech` (already wired, session 8b) works fully offline *if* the phone has that language's voice data already downloaded via system Settings (Settings -> Language & input -> Text-to-speech output -> select Google's engine -> install the Hindi/Tamil/Telugu/Kannada/Malayalam voices while online, once). Nothing to build; this is a one-time setting, not a download link.
- **Speech-to-text**: this one WAS a real gap -- the Voice tab still required the server for transcription even in the "standalone" build (see session 8). Investigated and closed it:
  - Confirmed `dev.ffmpegkit-maintained:whisper-android:1.0.0` (prebuilt whisper.cpp AAR, already a Gradle dependency, unused until now) accepts WAV/MP3/FLAC "at any sample rate -- decoded and resampled internally" (verified from the library's own README via WebFetch, not assumed), which rules out the earlier worry about exact audio-format compatibility.
  - Its `Whisper.loadModel`/`loadModelFromAsset`/`transcribe` are Kotlin suspend functions with no plain-Java overload -- previously recorded as the reason on-device STT wasn't feasible without adding Kotlin to this Java-only project. - **Grounded generation + abstention** (`src/disaster_assistant/generation/`, `src/disaster_assistant/safety/`): retrieval -> evidence-sufficiency gate -> grounded Ollama call with citations, or a fixed abstention message with sourced emergency phone numbers, **in any of 6 languages**. Includes a structural (code-level, not just prompt-level) live-information guard (English-only detection).
- **Offline ASR** (faster-whisper "small", **CUDA-accelerated with automatic CPU fallback**) and **offline TTS, language-routed across 6 languages**: Piper for English/Hindi/Telugu/Malayalam; `facebook/mms-tts-tam` and `facebook/mms-tts-kan` (VITS, via `transformers`) for Tamil and Kannada, since Piper ships no voice at all for either (checked directly against its full voice list both times).
- **Full voice pipeline**, both CLI (`scripts/voice_ask.py`) and a **Streamlit UI** (`src/disaster_assistant/api/app.py`, text + voice tabs, the voice tab's browser mic recorder -- the user has since confirmed this works on their machine).
- **Cross-lingual pipeline verified end-to-end in Tamil and Hindi**: correct, grounded, same-language answers with matching speech output, retrieving from the English-only knowledge base via the multilingual embedding model -- for *some* questions. See Finding #14 for where this breaks down.
- **21 automated tests** (`tests/`, run with `pytest`), covering the tokenizer, abstention logic (including the cross-lingual case), chunking/page-range tagging, live-info detection, offline-config, and per-language config consistency. All passing.
- **Failure-mode hardening**, each one actually triggered and checked, not just reasoned about: missing index files, Ollama unreachable/model not pulled, silent/unintelligible audio (abstains safely despite a Whisper hallucination -- see Findings), corrupted/invalid audio file (now reports a clear error instead of being silently misreported -- see Findings), empty question.

## Findings from this session (observed directly, not assumed)

1. **A working Tamil TTS path exists: `facebook/mms-tts-tam`.** Piper (checked against its full voice list in the prior session) has no Tamil voice; this VITS model via `transformers` fills the gap, verified to produce valid, non-silent, correctly-paced Tamil audio.

2. **A real architectural bug: the abstention rule structurally blocked all non-English answers.** The BM25-overlap requirement in the abstention gate can never be satisfied by a Tamil query against an English-only corpus (different scripts, zero possible lexical overlap) -- so *every* Tamil question would have abstained regardless of transcription or retrieval quality, independent of the bug below. Fixed: the lexical-overlap requirement now only applies when the query's language matches the corpus's language (English); cross-lingual queries are gated on the dense-score floor alone. Covered by `tests/test_abstention.py`.

3. **A real tokenizer bug, fixed twice.** First pass: the BM25 tokenizer was `[a-z0-9]+`-only, silently producing zero tokens (and therefore BM25 score 0.00) for any Tamil text. Second pass, found by a failing test: the "fix" (`[^\W_]+` with Unicode) was *also* wrong for Tamil specifically -- Tamil words are base letters plus combining vowel-sign/virama codepoints, which Python's regex `\w` doesn't include, so it fragmented every word into pieces at each combining mark. Final fix: tokenize by whitespace and strip edge punctuation per token, which never looks inside a non-space run and so can't fragment combining-mark sequences. Covered by `tests/test_tokenizer.py`.

4. **Whisper ASR accuracy is a genuine bottleneck for Tamil, and model size matters a lot.** On the same test utterance, "small" mis-transcribed "flood" (வெள்ளம்) as "jaggery" (வெல்லம்) and "house" (வீட்டிற்குள்) as a similar-sounding wrong word -- confidently (p=0.99). "medium" got "flood" right but still had one residual error. With the *correct* Tamil text, cross-lingual dense retrieval correctly surfaces the right citizen-facing passages and generation produces a substantive, accurate answer -- so the bottleneck is specifically ASR accuracy, not retrieval or generation. Trade-off: "medium" took dramatically longer than "small" on this hardware under current memory pressure (minutes vs. ~9s for an 8-second clip) -- kept "small" as the default rather than silently switching, since that latency is currently impractical, but this is now a documented, evidence-based trade-off rather than an unexamined default.

5. **Whisper hallucinates on silence (a known general Whisper behavior, now confirmed on this setup).** Pure silence was transcribed as the word "You" with low-but-nonzero confidence (~0.3). The existing low-confidence warning and the abstention gate together caught this safely -- the system never answered confidently based on a hallucinated transcript -- but this is a soft safety net (confidence threshold + abstention), not a fix to the hallucination itself.

6. **A real exception-handling bug: `av.error.InvalidDataError` (raised by faster-whisper's audio decoding on a corrupted file) is itself a subclass of `ValueError`.** The pipeline used a bare `ValueError` to signal "empty transcription" from silence; because of this inheritance, a genuinely corrupted/unreadable audio file was being silently misreported as if it were just silence, with no real error message. Fixed with a dedicated `EmptyTranscriptionError` instead of overloading `ValueError`. A good general lesson: don't catch a builtin exception type to mean one specific thing unless you're sure no unrelated library exception shares that ancestry.

7. **Windows console encoding**: printing Tamil (or most non-Latin) text crashed with `UnicodeEncodeError` on Windows' default `cp1252` console codepage. Fixed by reconfiguring stdout/stderr to UTF-8 at the top of the CLI scripts.

8. **Real, verified Tamil Nadu emergency contact numbers found and wired in**: TNSDMA state control room (1070) and district control room (1077), read directly from `tnsdma.tn.gov.in`'s own site (not independently cross-checked against a second source -- flagged in `data/metadata/documents.json`'s `verified_contacts`), alongside the well-known national 112. These now appear in the abstention message instead of only the generic national number, pulled from one place (the registry file) rather than hardcoded twice.

9. **A generation quality quirk, not fixed**: in one Tamil answer, the model inserted a stray Hindi/Devanagari word ("नल") into otherwise-Tamil output, and in another it added English parenthetical glosses of its own Tamil sentences unprompted. Noted, not addressed -- would need prompt tuning or a different model to investigate properly.

10. **Ollama *is* using the GPU, contrary to what the first session's "torch is CPU-only, nothing uses the GPU" note implied.** `curl localhost:11434/api/ps` shows `gemma4:e4b` loaded with `size_vram` ~3GB -- Ollama bundles its own CUDA-capable llama.cpp runtime, entirely independent of the project's Python `torch` install (which genuinely is CPU-only, for the embedding model and Tamil TTS). The two are separate GPU-usage questions; conflating them would have been wrong.

11. **The real generation-latency bottleneck was the model's reasoning trace, not model load or retrieval.** Measured via Ollama's own stats on a real grounded prompt: prompt processing (1223 tokens of evidence+instructions) took 0.78s; generation took 19.4s for 931 output tokens -- far more than the "2-5 sentence" answer the prompt asks for, because `gemma4:e4b` is a hybrid reasoning model emitting an internal thinking block by default. Setting `"think": false` in the Ollama API request (now the default in `ollama_client.py`) cut that to ~9 tokens / ~2.5s for a comparable short test, and the full grounded-answer latency from ~22-27s to ~4.6s, with no apparent loss in answer quality (same correct, grounded content before/after, in both English and Tamil). This is now the default; the earlier "~30s cold load" latency notes from the first two sessions were measuring a real but much smaller effect than this one.

12. **ctranslate2 CUDA support for faster-whisper: fixed.** `device="cuda"` initially failed with `Library cublas64_12.dll is not found or cannot be loaded` -- the NVIDIA driver alone isn't the CUDA runtime. Installed `nvidia-cublas-cu12`/`nvidia-cudnn-cu12`/`nvidia-cuda-runtime-cu12` (pip packages providing the actual DLLs). Still failed at first even with those installed and their directories registered via `os.add_dll_directory` -- ctranslate2's CUDA library loading apparently doesn't consult directories registered that way. Prepending the same directories to the process `PATH` instead fixed it. Effect: ASR dropped from ~8-9s to ~1.6-2.6s for an 8s clip. `audio/asr.py` now does this PATH setup automatically (no-op if the nvidia packages aren't installed) and falls back to CPU if a CUDA compute call still fails (tested by stripping the PATH entries back out and confirming a clean fallback, no crash).

13. **Ollama cold-start (~30s) is now the single largest remaining latency item**, once it actually happens (first call after the model's been idle past `keep_alive`, or Ollama's own startup). Not addressed further this session -- `keep_alive=30m` reduces how often it recurs within a sitting but doesn't eliminate the first paid instance.

14. **Cross-lingual retrieval quality varies by specific concept/word, not just by language, and this is now diagnosed, not just observed.** Testing all 4 new languages on "what should I do during an earthquake" (Hindi/Telugu/Kannada/Malayalam) retrieved the *same wrong* passage for all four -- a generic institutional "community disaster-preparedness/early-warning" passage from the cyclone guidelines (`ndma_cyclones_2008_p138`), not any earthquake-specific content. The same languages retrieve *correctly* for flood questions (verified directly for Hindi). Mechanism: that passage's broad, hazard-agnostic vocabulary makes it a semantic "hub" that generic-sounding disaster queries gravitate toward in the embedding space when the query's specific hazard word doesn't align precisely enough with the matching English content -- for "earthquake" specifically, `multilingual-e5-small`'s cross-lingual alignment in these four languages apparently isn't precise enough to beat that hub. Tamil was not tested on this exact question, so it is not confirmed to be exempt. **Not fixed this session** -- would need either a better/larger embedding model, query translation to English before retrieval (CLAUDE.md SS8.4's own suggested comparison), or reranking; any of those adds latency or complexity, a real tension with "fast."

15. **ASR mis-transcription affects Hindi too, not just Tamil** (Finding #4, prior session). A Hindi flood question was transcribed with real word-level errors (e.g. "बाढ़" flood -> "भार्द", a non-word) despite high reported confidence (p=1.00). The system responded safely -- it declined to answer rather than guessing -- but this confirms the ASR-accuracy caveat generalizes across the new languages, not just Tamil.

- No systematic multi-language evaluation exists for any of the 5 non-English languages -- everything above is a small number of manual spot-checks, consistent with "no formal evaluation yet." Finding #14 in particular shows spot-checks can miss real, consistent failures that a real evaluation set would catch systematically.
